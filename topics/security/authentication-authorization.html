인증과 인가

쿠키 / 세션 / 토큰?

  • 왜인지는 모르겠으나, 인터넷 상에서 쿠키, 세션, 토큰을 동일 위계에 놓고 비교하는 포스팅이 많음.
  • 실제 위계를 생각해보면, 아래와 같이 나누는 것이 더 적절함.
    • (인증 방식에 따른 분류) 세션 기반 인증(세션 ID) / 토큰 기반 인증(JWT)
    • (저장 수단에 따른 분류) 쿠키 / 웹스토리지 / 메모리
    • (전달 수단에 따른 분류) Cookie 헤더 / Authorization 헤더

저장 수단별 특징

메모리

  • 메모리를 사용하는 방식으로도 토큰(세션ID) 보유 가능
  • 단, 페이지 이동 시 데이터 보존이 안됨. 단, SPA 구조에서는 페이지가 유지되므로 사용하기도 함.이 경우, 새로고침 시 데이터 보존이 안됨.
  • SPA 구조에서는 오히려 적절한 시간 후에 휘발된다는 점을 역이용하여 Access Token을 메모리에 보관하고, Refresh Token을 쿠키에 보관하는 방식을 채택하기도 함탈취할 토큰 자체가 없어진다는 것이 보안에 유리
  • XSS 위협이 존재하나, 표준 API를 통해 쉽게 읽을 수 있는 WebStorage에 비해 탈취가 상대적으로 어려움.

cookie

  • 서버에서 클라이언트에게 전송하는 데이터
  • 서버에서 응답 헤더에 Set-Cookie: <k>=<v> 형태로 제공
  • 클라이언트는 헤더에 Cookie: <k1>=<v1>;<k2>=<v2> 형태로 매번 요청에 들어감.
  • 문자열로만 저장 가능하며, 최대 4kb 제한
  • (스니핑 위협 존재) secure 플래그로 의도치 않은 HTTP 요청에 대해 쿠키 미발송
  • (XSS 위협 존재) HttpOnly 플래그로 브라우저에서 실행되는 JavaScript가 쿠키에 접근하지 못하도록 방지
  • (CSRF 위협 존재) SameSite 플래그로 다른 Origin(도메인)의 요청은 쿠키 미발송

Session cookie

  • 웹브라우저 종료 시 제거

Persistent cookie

  • 영구적으로 유지되는 쿠키.
  • Expires로 만료시간을 지정 가능.
  • Max-Age로 유지기간을 지정 가능.

Web Storage

  • HTML5에서 제공하는 저장소 API
  • OS 파일 시스템 위에 데이터베이스로 저장됨firefox의 경우 SQLite
  • (Origin, Key, Value) 테이블 구조를 가져, Origin(도메인)별로 저장됨.
  • 문자열로만 저장 가능하며, 보통 최대 5mb 제한단, 객체나 배열을 JSON.stringify()로 변환하여 문자열로 저장 가능
  • (XSS 위협 존재) JavaScript로 읽어야 하는 구조 상 XSS에 취약함. 단, DOM 조작 API 중 innerHTML이 아닌 textContent를 사용하여 안전하게 문자열을 렌더링하는 방식으로 방지 가능React.js 등 프레임워크는 기본적으로 이런 방식이 기본값
  • (CSRF 위협 없음) 쿠키처럼 자동 전송이 아닌, 로컬에서 직접 토큰(세션ID)을 얻어서 Authorization 헤더에 넣는 방식이므로 안전.

Local Storage

  • 도메인에 종속됨
  • 영구적이므로 직접 삭제해야 함.

Session Storage

  • 도메인에 종속됨
  • 현재 세션(탭)에도 종속됨. 다른 탭에서 열면 두 세션 스토리지에서 읽는 값은 달라짐
  • 세션을 종료하면 삭제됨

인증 방식별 특징

  • 최초 로그인은 ID/PW를 통해 진행하지만, 민감한 정보(ID/PW)의 보호를 위해 이후 단계에서는 민감 정보 대신 세션ID 혹은 토큰을 사용한다.
  • 세션 ID나 토큰에 유효기간을 부여하여 탈취가 되더라도 공격할 수 있는 시간을 제한시킨다.

세션 기반 인증

  • 서버의 DB에서 관리하는 고유한 ID인 세션ID를 클라이언트에게 제공
  • 서버가 세션ID를 Key로 저장하고, 그 외 정보를 Value로 저장하는 K-V 구조
  • 매번 서버 DB서버에 확인 요청을 날려야 하므로 서버에 부하를 일으킴Stateful

토큰 기반 인증

  • 서버가 고유한 토큰을 발급하여 클라이언트에게 제공
  • 토큰 자체에 정보가 담겨서 서버가 따로 관리할 필요 없음Stateless
  • 서버는 토큰이 변조되었는지 검증하는 절차만 가짐
  • 단, 토큰 자체의 길이가 길다는 단점이 있음

JWT

  1. Header
  2. Payload
  3. Signature
  • (Header) 토큰의 형식과 서명 알고리즘암호화가 안됨
  • (Payload) 사용자 및 인증·인가 정보암호화가 안됨
  • (Signature) Header와 Payload의 무결성 및 서명자 검증. 서버의 비밀키가 없으면 복호화 불가.
